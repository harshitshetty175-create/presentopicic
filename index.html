The order lifecycle — 7 states

Placed → Confirmed → Preparing → Ready for Pickup → Picked Up → Out for Delivery → Delivered. Every jump is validated on the server — a Placed order can never skip straight to Delivered, and every change is written to Order_Status_History.

Stop 1 · The problem it solves

The order that half-happened

A customer orders the last Paneer Tikka. The payment is recorded — then the app crashes before the order and stock update are saved. Money taken, no food, stock still showing available. The next customer orders the same last piece too.

Payment saved ✓

Payments row created — ₹349 recorded as paid.

Order lost ✕

No row in Orders or Order_Items. The kitchen never sees it.

Stock wrong ✕

Inventory still shows 1 left — so it gets sold again. Overselling.

The database is left inconsistent — and this is exactly what Transaction Management in FoodFlow prevents.

It manages

Every checkout from BEGIN to COMMIT — or ROLLBACK if anything fails.

It protects

The database stays consistent through crashes, failures and many users ordering at the same time.

It guarantees

All or Nothing — order, payment and stock change together, or none of them do.

Stop 2 · The unit of work

One order = one transaction

Placing an order is a single logical unit of work. Tap each step to see what the database actually does — prices are always recalculated on the server, never trusted from the browser.

BEGIN TRANSACTION; -- 1. check stock with a conditional update (no overselling) UPDATE Inventory SET stock = stock - 1 WHERE food_item_id = 12 AND stock >= 1; -- 2. order + items (with price snapshots) + payment, together INSERT INTO Orders ...; INSERT INTO Order_Items ...; INSERT INTO Payments (method, status, reference) VALUES ('UPI_SIMULATED', 'SUCCESS', 'SIM-…'); COMMIT; -- any failure anywhere → ROLLBACK everything

An idempotency key on checkout means a double-tap or a retry can never create the same order twice.

ER diagram — who connects to whom

The core relationships of FoodFlow. One customer places many orders; one order has many items; every delivery and payment belongs to exactly one order.

One customer, many orders
RESTAURANTS 1 — N FOOD_ITEMSrestaurant_id (PK) → Food_Items.restaurant_id (FK)
ORDERS 1 — N ORDER_ITEMSorder_id (PK) → Order_Items.order_id (FK)
Items keep name + price snapshots

Amount · method · SIM reference · status
ORDERS 1 — 1 DELIVERIESpartner_id (FK) · pickup & delivery timestamps
USERS M — N FOOD_ITEMSThrough Favourites & Reviews
junction tables resolve the many-to-many
CATEGORIES 1 — N FOOD_ITEMScategory_id (FK) · 10 categories, 50 dishes
COUPONS 1 — N COUPON_USAGEusage tracked per user + order, so a coupon can't be reused silently
ORDERS 1 — N STATUS_HISTORYEvery status change logged with timestamp — the audit trail of an order

Normalisation in one line: no repeating groups (1NF) → no partial dependencies (2NF) → no transitive dependencies (3NF). Restaurant details live once, in Restaurants — never copied into every order.

Stop 6 · The four promises

ACID, the FoodFlow way

Four guarantees that make a transaction trustworthy. Tap each letter — every one is mapped to a real FoodFlow behaviour.

Concurrency — the last-item race

Two customers, one Paneer Tikka left. A conditional update — UPDATE … WHERE stock >= 1 — lets exactly one succeed. The other gets a clean "out of stock". No overselling, ever. Try it in the live demo next.

Recovery

InnoDB's redo and undo logs let MySQL redo committed orders and undo uncommitted ones after a crash — so a power cut mid-checkout can never leave a half-order behind.

How it works in the project

Order placed → a row is inserted into Notifications for the restaurant. Status changes add rows for the customer and delivery partner. Persist-first means nothing is lost if the live connection drops — the feed is correct on the next load.

Honest scope

FoodFlow persists notifications and shows them on load / navigation. It does not claim Socket.IO push — that distinction is stated in the project itself.

Stop 10 · Wrap-up

All or nothing — that's the whole idea

An order is one unit of work. It flows through seven states, protected by the four ACID guarantees — and it either commits completely, or it rolls back completely. Nothing in between, ever.

Remember 1

Transaction = one logical unit of work: Begin → operations → Commit, or Rollback.

Remember 2

21 tables, 3NF — one fact in one place, joined by foreign keys, priced by snapshots.

Remember 3

ACID + conditional stock updates — the reason the last Paneer Tikka can only ever be sold once.
